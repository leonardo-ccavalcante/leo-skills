**Reforços (19)**

- `SKILL.md:31` · Modelo e effort por etapa — Para Claude, a alavanca por etapa é modelo + effort (não temperatura): etapas simples/alto volume em Haiku 4.5 ou effort low; síntese em effort medium/high. Atenção ao cache: trocar effort (ou a configuração de thinking) entre requisições invalida o cache daquele ponto em diante (em alguns modelos também tools e system), mudar o formato de saída invalida o cache inteiro, e o cache é por modelo. Por isso, só etapas com o mesmo modelo, effort e formato de saída aproveitam um prefixo compartilhado em cache (ex.: as chamadas do map); onde houver suporte (Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5; nos demais dá 400), usar a mudança de effort por mensagem (beta), que preserva o prefixo. (optimizing-for-cost-and-intelligence, "What breaks the cache"); (effort, "Per-message effort (beta)")
- `SKILL.md:31` · Quando combinar modelos — Dividir entre modelos só compensa quando a dificuldade varia entre etapas; cadeia dependente de dificuldade uniforme fica melhor num só modelo bem ajustado. Antes de montar multi-modelo, fazer um sweep de effort no modelo atual (é a linha de base a bater). (optimizing-for-cost-and-intelligence, "Combine models")
- `SKILL.md:34` · Detecção barata + processamento caro — Quando o resultado é verificável, rodar tudo em effort baixo e reexecutar só as falhas em effort alto (mesmo padrão de curto-circuito, aplicado ao effort). (optimizing-for-cost-and-intelligence, "Re-run failures at higher effort")
- `SKILL.md:35` · Quando encadear — Os docs do Claude confirmam: com thinking adaptativo e subagentes, a maior parte do raciocínio multietapas é interna; encadeamento explícito vale para inspecionar saídas intermediárias ou impor uma estrutura de pipeline, e o padrão mais comum é self-correction (draft → review → refine) em chamadas separadas. (claude-prompting-best-practices, "Chain complex prompts")
- `SKILL.md:38` · Contexto pesado compartilhado vs. prompt caching — Com prompt caching, o contexto repetido entre chamadas custa 10% do preço de input (2,5% no Fable 5.1 e no Mythos 5.1, 5% no Opus 5.5; models-overview, "Compare models") se vier como prefixo byte-idêntico: ordenar tools → system → contexto compartilhado estável → parte variável por etapa no último turno do usuário. Isso reduz o custo de 'duplicar contexto' que o skill usa como motivo para não encadear. Vale só entre chamadas com o mesmo modelo, effort e formato de saída (ver o item da linha 31). (optimizing-for-cost-and-intelligence, "What breaks the cache")
- `SKILL.md:42` · "Manter num prompt só com CoT" em modelos com thinking — Para Claude, "manter num prompt só" significa confiar no thinking adaptativo e subir o effort se o raciocínio ficar raso, não pedir um traço de CoT no texto da resposta (no Opus 5.5 e no Fable 5/Mythos 5 isso pode ser recusado com reasoning_extraction). Para inspecionar o raciocínio, ler os blocos de thinking com display "summarized". (prompting-claude-opus-5-5, "Prompts written for thinking disabled")
- `SKILL.md:63` · Saídas estruturadas nas fronteiras — Para Claude, usar o recurso Structured Outputs (ou tool com enum para classificação/roteamento) nas fronteiras tipadas da cadeia, não prefill (que retorna 400 a partir dos modelos 4.6). Lembrar que trocar ou ativar o formato de saída invalida o cache da conversa inteira; manter o mesmo schema entre chamadas que compartilham prefixo. (claude-prompting-best-practices, "Migrating away from prefilled responses")
- `SKILL.md:66` · Não adicionar etapas 'por segurança' — A auditoria de prompts da Anthropic confirma: instruções como "verify twice" e etapas obrigatórias escritas para modelos antigos são seguidas à risca pelos novos e só aumentam o custo; auditar a cadeia a cada troca de modelo (ex.: /claude-api prompt-audit). (optimizing-for-cost-and-intelligence, "Audit prompts against the current model")
- `SKILL.md:90` · Revisor com enquadramento/contexto diferente — No Fable 5/Mythos 5, em tarefas longas (agentes), verificadores separados com contexto novo tendem a superar a autocrítica; isso não torna a cadeia de dois prompts o padrão para uma tarefa curta como uma resposta de suporte. No Opus 5, não usar subagentes para re-checar o próprio trabalho por padrão. (prompting-claude-fable-5, "Recommended scaffolding changes")
- `SKILL.md:124` · Quantos exemplos o loop Jinja deve renderizar — O loop de 0 a N exemplos continua útil; para Claude, quando houver exemplos, mirar 3–5 relevantes e diversos no conjunto renderizado. (claude-prompting-best-practices, "Use examples effectively")
- `SKILL.md:134` · Delimitar entrada do usuário — No Opus 5.5, marcar texto colado pelo usuário com <pasted_content id="…"> … </pasted_content id="…"> (id aleatório curto gerado pela aplicação, a mesma na abertura e no fechamento, cada tag em sua linha) e adicionar a nota de sistema correspondente. As tags são texto simples e podem ser imitadas: é uma proteção entre outras, não substitui escapar o delimitador nem as defesas de `prompt-security`. (prompting-claude-opus-5-5, "Mark pasted text in user messages")
- `SKILL.md:136` · Renderização determinística e cache — Além da estética, whitespace estável importa para o cache: o prefixo precisa ser byte-idêntico entre chamadas do map. Renderizar partes fixas (persona, instruções, exemplos) primeiro e deixar o valor por item no fim; nada de timestamp/contador no topo. (optimizing-for-cost-and-intelligence, "What breaks the cache")
- `SKILL.md:151` · Documentos longos no topo na etapa reduce — No template de reduce, colocar os resumos (20k+ tokens) no topo, em <documents><document index="n">…</document></documents>, e a instrução/pergunta no fim. (claude-prompting-best-practices, "Long context prompting")
- `SKILL.md:155` · Map em lote — Se ninguém espera o resultado do map, enviar pela Batch API (50% de desconto, acumula com cache) em vez de fan-out síncrono. (optimizing-for-cost-and-intelligence, "Batch work that can wait")
- `SKILL.md:176` · Menos chamadas LLM, mais cola determinística — Os docs confirmam: se o trabalho é uma cadeia dependente, cabe num contexto e não tem cauda longa de custo em tarefas rotineiras, ou um modelo em effort menor já atinge a meta, não montar orquestração; e tabelas para calcular vão via Files API + code execution, não coladas no prompt. (optimizing-for-cost-and-intelligence, "Orchestrator strategy: delegate bulk work")
- `references/chain-design-patterns.md:36` · Roteamento com modelo menor e rótulos fechados — Para o classificador de rota, usar um modelo barato e rápido (Haiku 4.5 ou Sonnet 5 em effort low); retornar a rota via tool com enum ou structured outputs. Não usar Fable 5.1/Mythos 5.1 aqui: são os mais caros e não aceitam uso forçado de tool (tool_choice any/tool retorna 400), então o enum só pode ser imposto por structured outputs. (claude-prompting-best-practices, "Migrating away from prefilled responses")
- `references/chain-design-patterns.md:75` · Plan-then-execute com modelos diferentes — Mapear para as estratégias oficiais: advisor (executor barato consulta um modelo de fronteira nas decisões difíceis, via advisor tool) ou orchestrator (modelo de fronteira planeja e delega a workers baratos, ex.: Sonnet 5). Medir contra o modelo mais forte sozinho em effort low. (optimizing-for-cost-and-intelligence, "Combine models")
- `references/jinja2-prompt-template.md:70` · Delimitar entrada do usuário no template — Para Opus 5.5, trocar <user_input> por <pasted_content id="{{ rand_id }}"> … </pasted_content id="{{ rand_id }}"> quando o conteúdo foi colado de outra fonte, mais a nota no system prompt. (prompting-claude-opus-5-5, "Mark pasted text in user messages")
- `references/jinja2-prompt-template.md:76` · Autoescape desligado preserva tags XML — Para Claude isso é essencial: a estrutura do prompt usa tags XML (<instructions>, <context>, <example>, <document>), que o autoescape destruiria; escapar só o valor do usuário quando necessário. (claude-prompting-best-practices, "Structure prompts with XML tags")
