# Input formats — tagged JSON, state files, and every CSV/Excel spec

Read this BEFORE loading any user file or building input JSON. Every spec below is
derived from the script source; when a file doesn't match, the fix is a conversation
about column mapping — never a guess.

## When NOT to use

- **Don't build a file for conversation-stated numbers.** Inline tagged JSON via
  `--inputs` is the primary path; files are for exports the user already has —
  transcription adds a failure surface and hides provenance.
- **Don't force an export into a spec it doesn't fit.** An MRR file with only totals
  (no per-movement columns) can't feed the ARR bridge — use point metrics instead;
  reshaping data to satisfy a schema invents information.
- **Don't store computed results in `.fa.json`.** State files hold *inputs*; outputs
  are regenerated by rerunning, and stored outputs go stale while looking fresh.

## 1. The tagged-value schema

Every input is an object with `value` and `status` — a number without provenance
cannot be challenged later. Optional fields: `basis`, `source_url`, `confidence`
(`low|medium|high`). One example per status:

```json
{
  "mrr_now":            {"value": 42000, "status": "user"},
  "gross_margin_pct":   {"value": 78, "status": "public", "source_url": "https://investor.example.com/10k-2025"},
  "monthly_churn_rate": {"value": 0.025, "status": "assumption", "basis": "SMB SaaS midpoint; not yet measured"},
  "cac":                {"value": null, "status": "unknown"}
}
```

Rules enforced by `fin_common.parse_inputs` and `fa.sh validate`:

- `unknown` ⇒ `value` must be `null` (parse error otherwise) — an "unknown with a
  value" is a tag lying about itself. A number you have gets one of the other tags.
- A `null` value under any other status is downgraded to `unknown` with a warning at
  parse time and is a hard **error** in `fa.sh validate` — fix the tag.
- `assumption` should carry a `basis` (validator warns): an assumption whose
  rationale isn't stated can't be challenged, which defeats the tag system.
- `public` should carry a `source_url` (validator warns). A benchmark recalled from
  memory is NOT `public` — it is an `assumption` with the recollection as its basis.
- Bare scalars (`"mrr_now": 42000`) are auto-tagged `user` with a warning. Prefer
  explicit tags: the auto-tag asserts "the user stated this", false for estimates.
- `calculation` is an *output* status only — never write it into an input file.

## 2. The `.fa.json` state file

For any multi-input analysis, save the agreed tagged inputs as
`<analysis-name>.fa.json` in the working directory — resumable and auditable:

```json
{
  "analysis": "acme-saas-health-2026-08",
  "currency": "USD",
  "date": "2026-08-18",
  "inputs": {"mrr_now":   {"value": 42000, "status": "user"},
             "mrr_prior": {"value": 39500, "status": "user"}}
}
```

- Allowed metadata keys (from `validate_state.py`): `analysis`, `domain`,
  `currency`, `country`, `notes`, `date`. Anything else must be a tagged input.
- Resume by passing the file straight to any script: `--inputs-file acme.fa.json` —
  `load_inputs` unwraps the `{"inputs": {...}}` wrapper automatically.
- Validate after every edit, *before* computing: `fa.sh validate acme.fa.json`
  (exit 3 on errors, 0 clean, `--json` available). A tag error caught here costs one
  line; caught in a report it costs the report's credibility.
- List-valued inputs (e.g. `benefit_series`) pass validation structurally; the
  consuming script checks them.

## 3. Per-script file specs

`load_table` strips and lowercases every header, so specs below are
post-normalization names. Missing required columns abort with the found-columns list
— that is your cue for the mapping conversation (section 4), not a silent rename.

### `fa.sh saas --mrr-file` — ARR bridge

Required columns: `month`, `new_mrr`, `expansion_mrr`, `contraction_mrr`,
`churned_mrr`. Optional: `mrr_end`.

```csv
month,new_mrr,expansion_mrr,contraction_mrr,churned_mrr,mrr_end
2026-01,3000,800,200,1100,41500
2026-02,2500,900,150,1300,43450
2026-03,2800,750,300,1200,45500
```

- The chain needs an anchor: `mrr_end` on the **first row** or `--starting-mrr
  <float>`. Without one the script refuses — later months would inherit an invented
  base. Blank movement cells become 0 (warned).
- When reported `mrr_end` disagrees with the computed bridge, the reported figure
  wins and the residual is warned as unmodeled movement — relay that warning; it
  usually means a movement category is missing from the file.
- Trailing-12-month NRR/GRR need ≥ 13 rows; fewer are skipped, not approximated.

### `fa.sh saas --cohort-file` — retention triangle

Required columns: `cohort_month`, `months_since_start`, `customers`. An `mrr` column
is accepted but retention here is customer-based.

```csv
cohort_month,months_since_start,customers
2025-06,0,40
2025-06,1,36
2025-07,0,52
```

Cohorts without a positive month-0 count are excluded (warned) — a retention row
without its own denominator is meaningless. `--mrr-file`, `--cohort-file`, and
`--inputs`/`--inputs-file` are mutually exclusive: one mode per run.

### `fa.sh projection --drivers-file` — driver JSON

Takes the RAW nested driver JSON below (also accepted via `--inputs`/`--inputs-file`
— exactly one source), NOT a flat tagged dict. Any scalar may still be tagged
`{"value":..,"status":..,"basis":..}` — tags are echoed for provenance, math uses
the value. Schema (from `projection.py`):

```json
{
  "months": 36,                  // optional, default 36, capped at 120
  "starting_cash": 30000,        // opening cash; absent => cash track skipped (P&L still runs)
  "currency": "USD",             // echoed only, never converted
  "activities": [                // >=1 usable activity is the critical gate
    {"name": "subscriptions",
     "price": 99,                // per unit, accrual
     "unit_variable_cost": 8,    // per unit; missing => 0 (warned)
     "volume_start": 5,          // units in month 1
     "volume_growth_pct_monthly": 10}   // percent (10 = 10%), compounding
    // OR "volumes": [5, 6, 7, ...]     // explicit per-month units; overrides growth;
    //                                  // a short list holds its last value (warned)
  ],
  "opex_lines": [{"name": "hosting", "monthly_amount": 400,
                  "start_month": 1,           // default 1
                  "annual_growth_pct": 0}],   // percent; steps at months 13, 25...
  "payroll": [{"role": "founder", "monthly_gross": 4000, "count": 1, "start_month": 1,
               "employer_burden_pct": 0}],    // fraction 0-1; > 1.5 read as percent/100 (warned)
  "capex": [{"name": "laptop", "amount": 3000, "month": 1,
             "amortization_months": 36}],     // straight-line from its month; missing => 36 (warned)
  "loans": [{"principal": 20000, "annual_rate": 0.12, "months": 36,
             "start_month": 1}],   // drawdown in at start_month, then constant payment (finmath)
  "funding": [{"amount": 50000, "month": 1}],
  "tax_rate_pct": 0.15,          // fraction of positive pre-tax income, monthly approximation;
                                 // > 1 read as percent/100 (warned); missing => taxes 0 + p3 gap
  "dso_days": 0,                 // customer payment delay; cash shifts by round(days/30) months
  "dpo_days": 0                  // supplier payment delay, same shift
}
```

`--months N` overrides `months` without editing the file, so saved drivers stay
canonical across scenario horizon changes.

### `fa.sh ratios` — tagged statement lines (no CSV)

Ratios take tagged JSON, not tables — statement lines come one-per-field so each
carries its own tag. Fields (all optional; the script computes what it can) —
income: `revenue`, `cogs`, `gross_profit`, `operating_expenses`, `operating_income`,
`depreciation_amortization`, `ebitda`, `interest_expense`, `pretax_income`,
`tax_expense`, `net_income`; balance: `cash`, `accounts_receivable`, `inventory`,
`current_assets`, `total_assets`, `accounts_payable`, `current_liabilities`,
`total_debt`, `total_liabilities`, `total_equity`.

Prior period via `--prior-inputs '<json>'` or `--prior-inputs-file fy24.fa.json`
(same fields and tagging; not both flags) — it unlocks average-based turnover ratios
and YoY deltas; without it the script uses period-end values and says so.
`gross_profit`, `operating_income`, `ebitda` derive from upstream lines when absent
(warned) — don't re-ask for numbers already implied.

### `fa.sh ops unit-cost --costs-file` + `--volume-file` — monthly trend

`--costs-file` columns: `month`, `cost_category`, `amount`. `--volume-file` columns:
`month`, `volume`. `--volume-file` requires `--costs-file`; costs alone trend the
pool totals with unit cost skipped. Two separate files, shown side by side:

```csv
month,cost_category,amount     |   month,volume
2026-05,salaries,38000         |   2026-05,1210
2026-05,tooling,2400           |   2026-06,1180
2026-06,salaries,38000         |   2026-07,1245
```

Without files, `ops unit-cost` takes tagged inputs: `cost_pool` (a category→amount
map; each amount may itself be tagged), `driver_volume`, `driver_name`.

### `fa.sh ops cost-to-serve --file`

Columns: `segment`, `cost`; optional `revenue`. Duplicate segment rows are summed —
un-aggregated exports are fine as-is.

```csv
segment,cost,revenue
enterprise,52000,310000
smb,64000,120000
self-serve,18000,95000
```

### `fa.sh ops headcount --demand-file`

Columns: `month`, `volume` (same 3-row shape as the volume file above). Capacity
drivers ride alongside as tagged inputs: `aht_minutes`, `shrinkage_pct` and
`occupancy_target` (0-1 fractions), `hours_per_fte_month` (default 160, injected as
a tagged assumption), `service_buffer_pct` (fraction, default 0), and
`loaded_monthly_cost_per_fte`.

### `fa.sh ops variance --file`

Columns: `period`, `category`, `budget`, `actual`; optional `type` (`cost` or
`revenue`, default `cost` — favorability flips by type, so tag revenue lines or an
over-plan revenue month will be reported as unfavorable).

```csv
period,category,budget,actual,type
2026-07,payroll,52000,54100,cost
2026-07,cloud,8000,7200,cost
2026-07,services,30000,28500,revenue
```

## 4. Excel rules and column mapping

- `load_table` reads `.xlsx`/`.xls` via pandas (anything else as CSV) and lowercases
  + strips every header. Keep **one table per sheet** starting at A1 — only the
  first sheet is read, and title/merged rows above the header become garbage columns.
- When a file doesn't match a spec, SHOW the user the header row exactly as found
  (the error message lists it) and agree the mapping column by column. Record agreed
  mappings as **user decisions** in the state file's `notes` — a mapping is itself an
  input with provenance. Never guess column semantics: "amount" might be gross or
  net, "churn" logos or dollars — a wrong guess poisons every downstream number
  while looking perfectly computed.

## 5. Currency and units

- Scripts are **currency-agnostic**: no conversion, ever. Fix one currency per
  analysis, record it in the state file's `currency` key (and the projection's
  `currency` driver), and send mixed-currency files back for conversion — silently
  summing two currencies is arithmetic that lies.
- Percentage conventions vary **by field**, and the code wins over intuition:
  **0-1 fractions** — `monthly_churn_rate`, `gross_margin_pct` in `unit-economics`;
  `tax_rate_pct`, `employer_burden_pct`, loan `annual_rate` in `projection`;
  `shrinkage_pct`, `occupancy_target`, `service_buffer_pct`, `discount_rate_annual`
  in `ops`. **Percent points (80 = 80%)** — `gross_margin_pct`,
  `net_profit_margin_pct`, `monthly_growth_pct` in `saas`;
  `volume_growth_pct_monthly`, `annual_growth_pct` in `projection` drivers.
- The trap: `saas` accepts `gross_margin_pct: 0.8` without complaint and reads it as
  0.8%, silently gutting LTV. Check the target script's convention before reusing a
  value across scripts, and read every envelope's `warnings` — the normalization
  heuristics announce themselves there.
- Outputs may be `_pct`-named and scaled to percent points regardless of input
  convention; echo them verbatim, never rescale by hand.

## Worked CLI examples

```bash
FA=~/.claude/skills/financial-analysis/scripts/fa.sh

# Inline tagged inputs, mixed provenance
$FA saas --inputs '{
  "mrr_now": {"value": 42000, "status": "user"},
  "mrr_prior": {"value": 39500, "status": "user"},
  "churned_mrr": {"value": 1300, "status": "user"},
  "expansion_mrr": {"value": null, "status": "unknown"},
  "gross_margin_pct": {"value": 78, "status": "assumption", "basis": "user estimate"}}' --json

# State-file round-trip: validate, then compute from the same file
$FA validate fy25.fa.json
$FA ratios --inputs-file fy25.fa.json --prior-inputs-file fy24.fa.json --json

# File modes
$FA saas --mrr-file mrr_movements.csv --starting-mrr 38700 --json
$FA saas --cohort-file cohorts.xlsx --json
$FA projection --drivers-file drivers.json --months 24 --json
$FA ops unit-cost --costs-file support_costs.csv --volume-file tickets.csv --json
$FA ops cost-to-serve --file segments.csv --json
$FA ops variance --file budget_vs_actual.csv --json

# File + tagged drivers together (headcount)
$FA ops headcount --demand-file demand.csv --inputs '{
  "aht_minutes": {"value": 11, "status": "user"},
  "shrinkage_pct": {"value": 0.3, "status": "assumption", "basis": "typical support org"},
  "occupancy_target": {"value": 0.85, "status": "user"},
  "loaded_monthly_cost_per_fte": {"value": 7800, "status": "user"}}' --json
```

## Report additions (extends the SKILL.md skeleton)

When file inputs were used, the **Method note** gains a data-provenance block — a
reader must be able to reproduce the load, not just the math — and **Inputs &
assumptions** names the state file and its `fa.sh validate` result (error/warning
counts) so the next session resumes from a file known to be clean.

```markdown
### Data provenance
| File | Consumed by | Rows | Column mapping (user-agreed) | Validation |
|---|---|---|---|---|
| mrr_movements.csv | saas --mrr-file | 14 | "net adds"→new_mrr | anchor: mrr_end row 1 |
```
